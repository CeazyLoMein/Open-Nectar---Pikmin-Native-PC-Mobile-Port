# Shared solo-save and co-op recovery plan - agreed scope

LATEST USER DECISION (October21): Keep normal saving for the current P1 bug-fix retest. After representative fresh-save validation, start the co-op prototype and design ONE snapshot/recovery system serving solo autosaves and co-op recovery. User briefly accepted ship-return checkpoints but then stated a preference for exact-scene resume; the ship-reset design is NOT the final target. No timed mid-day autosave, ship-reset checkpoint or new day-end autosave is implemented in this batch.

Why the existing card cannot simply be saved every two minutes: MemoryCard::writeCurrentGame writes PlayState plus PlayerState::saveCard, including previously prepared generator cache and Onion stock. That is a between-days checkpoint, not current action/FSM state. Generator-cache beginSave/endSave moves live/dead lists, and playerState saveCard clears tutorial mode; these are not side-effect-free arbitrary-tick snapshot APIs. Avoid calling day-end cleanup just to capture a mid-day file.

Existing netplay is not a complete persistence shortcut: GekkoSaveEvent in pc_netplay_session.cpp writes an8-byte frame handle/hash; GekkoLoadEvent aborts because window0 lockstep forbids loads. pc_record is camera/trailer tooling. pc_input_log records pads/yaw/extensions but neutralizes input paths such as mouse/touch outside its format. These do not already provide exact mid-day iPhone recovery. PC_ONLINE_ENABLED remains0 and iOS NECTAR_ONLINE remains OFF.

Design direction (proposal, not implemented/runtime verified):

- One phone owns authoritative campaign/world decisions; the other receives state and sends commands. Shared Onion withdrawals must be atomic host transactions, with separate squad ownership/allowances. Each phone renders only its own camera. No host migration or independent offline campaign branches in the first version.
- Guest disconnect while host remains alive: pause host simulation, retain both squads/world, reconnect using session token and a state keyframe. Short retained-session resume can be simpler than cold disk restore. A newly relaunched guest still needs initial world synchronization; never assume a socket reconnect alone rebuilds its game.
- Host crash/closure: recover from the latest validated disk snapshot; progress since its capture can be lost. Immediate seamless continuation cannot be promised after a host process dies. A server relay/matching solution may be needed across NAT; good connection alone is not a universal connectivity guarantee.
- Shared snapshot uses versioned data and stable entity IDs, not raw pointers, vtables or a heap dump. Capture at a safe simulation-tick boundary. Store clock/day/area, RNG, campaign parts/Onions, actors and health/hazards, seeds, jobs/AI state, carrying/attachment/target relationships, bombs, gates/bridges and pending gameplay transactions. Defer during unsafe loads/cutscene transitions until the last complete state can be preserved consistently.
- Rebuild native models/render/audio handles after load; do not serialize GL framebuffers or stale audio pointers. Validate entity IDs, counts, references and schema/game/build compatibility before applying. Keep normal card as fallback and two validated rotating snapshots; stage/checksum/flush/atomic commit so a failed write cannot replace the last good file.
- Solo and reconnect can share the full-state representation, while network updates may send smaller deltas. Avoid disk writes every network tick. Prototype capture/load for captain, squad, one enemy and a carried object first; then cover all behaviors. A schema file existing or a checksum matching is not proof a live world resumes correctly.
- Required recovery tests: same-day close/relaunch; corrupted/truncated snapshot fallback; pause/menu/background boundaries; enemy combat; carried pellet/part; bombs/hazards; seed/Onion accounting; simultaneous co-op withdrawals; guest reconnect; host crash; group area/cave transitions. No finale spoilers or mandatory final-boss test. P2 needs its own actor adapters and stronger cave/area/audio test matrix; reuse the container/recovery framework rather than assuming identical game state.

Research (primary sources, reviewedOctober21):

- [Mindustry NetServer](https://github.com/Anuken/Mindustry/blob/master/core/src/mindustry/core/NetServer.java) sends joining-world data and authoritative snapshots; [NetworkIO](https://github.com/Anuken/Mindustry/blob/master/core/src/mindustry/net/NetworkIO.java) defines world transfer. This is a useful reference for a shared-world game with many agents. It does not mean its Java serializer can be inserted into our native C++ game.
- [Factorio multiplayer rewrite](https://www.factorio.com/blog/post/fff-147) explains the complexity of joining/disconnecting in peer-to-peer lockstep; [joining/catch-up](https://www.factorio.com/blog/post/fff-149) transfers a saved map plus queued actions. Factorio still simulates deterministic state on clients; it is a different model from a host-only simulation with state replication. For our first together-only prototype, pause-and-resynchronize avoids a fast-forward catch-up requirement.

No external server deployed, accounts changed or networking enabled by this research.
